# data-catalog-mcp

## Demo

[https://youtu.be/r9nv5tqr924](https://youtu.be/r9nv5tqr924)

*A few empty commits in the history are leftover from testing the git MCP
tool (`git_commit` and friends) through an earlier chat REPL.*

Read-only MCP server for data cataloging and quality validation, framed as
**Meridian Holdings**' internal data catalog — five datasets across four
business units (mobile subscribers, retail sales, e-commerce, corporate HR),
each attributed to a plausible internal system of record rather than its
real (Kaggle/UCI) origin, since this is meant to be used the way an analyst
would use a real company catalog. Plus a web chat frontend and MCP host to
use it.

## Requirements

- Go 1.24+
- [Bun](https://bun.sh) (frontend)
- [Ollama](https://ollama.com) locally, or [Gemini](https://ai.google.dev) for embeddings; any OpenAI-compatible endpoint for chat
- `npx` (Node) for the official filesystem MCP server
- `python3`/`pip3` for the official git MCP server (`mcp-server-git`)
- [Docker](https://www.docker.com) (only if deploying `cmd/server`)

## Quick start

```bash
./scripts/setup.sh
```

Generates `.env` and `client.json` from their templates (fills in this
checkout's absolute path automatically) and builds `bin/data-catalog-mcp`.
Safe to re-run — never overwrites an existing file. Edit `.env` after if
you're not using the local-Ollama defaults (`LLM_*`/`EMBEDDINGS_*` vars —
see [the host + frontend](#the-host--frontend-cmdhost-frontend) below).

```bash
ollama pull nomic-embed-text      # embeddings, for search_catalog
ollama pull qwen2.5:7b-instruct   # or any other tool-calling-capable model

go run ./cmd/host                  # MCP host + streaming chat bridge, :8090
cd frontend && bun install && bun dev   # frontend: chat UI, talks to cmd/host
```

That's the whole setup. Everything below is detail on top of that.

## Architecture

Three pieces, talking standard MCP/JSON-RPC underneath (stdio locally,
HTTP for a remote server — see [Running `cmd/server` remotely](#running-cmdserver-remotely)):

| | |
|---|---|
| **`cmd/server`** | The data catalog itself — an MCP server. Parses `catalog.yaml`, reads the Parquet files, runs validations, does semantic search. Any MCP host can spawn it directly (locally) or reach it over HTTP (remotely) — it has no dependency on anything else here. |
| **`cmd/host`** | The MCP host. Connects one client per configured MCP server via `internal/client.Router` (data-catalog + the official filesystem/git servers), runs the tool-call loop against a chat model (`internal/agent`), and streams the whole thing to the browser as server-sent events. |
| **`frontend/`** | React + Vite chat UI. Talks only to `cmd/host` over HTTP — never spawns or talks to an MCP server directly. |
| **`cmd/client`** | One-shot CLI for calling a single tool directly, same Router underneath. |
| **`client.json`** | Declares the set of servers the Router connects to (`mcpServers`, gitignored — machine-specific paths/URLs). Generated by `scripts/setup.sh`, or copy `client.example.json` by hand. |

```
cmd/server/          MCP server entrypoint (stdio or HTTP, see TRANSPORT)
cmd/host/            MCP host — connects to client.json's servers, drives chat, serves SSE
cmd/client/          CLI, one tool call at a time
frontend/            chat UI (React + Vite + Tailwind), talks to cmd/host

internal/mcp/        MCP handshake + tool dispatch (initialize, tools/list, tools/call)
internal/tools/      tool implementations (list/describe/profile/validate/search/...)
internal/catalog/    catalog.yaml parsing
internal/data/       resolves catalog entries to Parquet files
internal/embeddings/ embeddings client for search_catalog (ollama + gemini providers)
internal/config/     env-based server config
internal/jsonrpc/    hand-rolled JSON-RPC 2.0 framing over a stream

internal/client/     MCP client: stdio (subprocess) + HTTP (remote URL) implementations, + Router
internal/llm/        provider-agnostic chat client (OpenAI-compatible wire format, streaming)
internal/agent/      tool-call loop shared by cmd/host: tool name resolution + StreamTurn

catalog/             catalog.yaml (data dictionary + quality rules)
data/                Parquet datasets (committed)
scripts/             setup.sh, Python helpers to build Parquet from raw CSVs
Dockerfile           builds cmd/server for remote deployment (see below)
```

## The server (`cmd/server`)

Tools implemented and working end to end:

- `ping` — health check
- `list_datasets` — registered datasets: description, origin, row count
- `describe_dataset` — one dataset's metadata, row count, column dictionary
- `profile_column` — per-column stats: type, nulls, distinct count, numeric
  min/max/mean, value frequencies or samples
- `validate_dataset` — runs the catalog's quality rules (`not_null`, `unique`,
  `range`, `allowed_values`, `regex`, `type_check`, `row_count`), reports violations
- `find_undocumented_columns` — Parquet columns missing from the catalog
- `search_catalog` — ranks datasets/columns by relevance to a query; semantic
  search via embeddings when configured, keyword matching otherwise

Config via environment variables / `.env`:

| Variable | Default | Description |
|---|---|---|
| `CATALOG_PATH` | `catalog/catalog.yaml` | Path to the catalog definition |
| `DATA_DIR` | `data` | Directory containing Parquet files |
| `TRANSPORT` | `stdio` | `stdio` (spawned locally) or `http` (served over the network) |
| `HTTP_ADDR` | `:8091` (or `$PORT`) | Listen address when `TRANSPORT=http` |
| `EMBEDDINGS_PROVIDER` | `ollama` | `ollama` (local) or `gemini` |
| `EMBEDDINGS_API_URL` | — | Base URL for the embeddings service (`ollama` provider only) |
| `EMBEDDINGS_MODEL` | — | Model name, e.g. `nomic-embed-text` (Ollama) or `gemini-embedding-001` (Gemini) |
| `EMBEDDINGS_API_KEY` | — | API key (unused for `ollama`, required for `gemini`) |

Every catalog doc (one per dataset/column) is embedded once per process and
cached in memory — `search_catalog` only embeds the query on every call
after that. The cache lives exactly as long as the process does; there's no
separate "reset," restarting the server is what recomputes it (e.g. after
editing `catalog.yaml`).

The server never transmits raw data — only catalog metadata and user queries
go to the embeddings service, so search works fully offline against a local
Ollama instance. If the embeddings service is unreachable, `search_catalog`
falls back to keyword matching instead of failing.

It's never run directly by hand for real use — an MCP host launches it,
either as a local subprocess over stdin/stdout, or (with `TRANSPORT=http`)
as an HTTP server a host reaches over the network. Same binary, same tool
logic either way — only the transport changes. For a manual sanity check
of the default (stdio) mode:

```bash
printf '%s\n%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05"}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"list_datasets","arguments":{}}}' \
  | ./bin/data-catalog-mcp
```

Or over HTTP:

```bash
TRANSPORT=http HTTP_ADDR=:8091 ./bin/data-catalog-mcp &
curl -s -X POST http://localhost:8091 \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"ping","arguments":{}}}'
```

### Regenerating the data

`data/*.parquet` is committed, so cloning is enough — this is only needed to
rebuild from raw sources:

1. Download the raw CSVs into `data/`: [Telco Customer Churn](https://www.kaggle.com/datasets/blastchar/telco-customer-churn),
   [Superstore Sales](https://www.kaggle.com/datasets/rohitsahoo/sales-forecasting),
   [Online Retail II](https://archive.ics.uci.edu/dataset/502/online+retail+ii),
   [HR Employee Attrition](https://www.kaggle.com/datasets/pavansubhasht/ibm-hr-analytics-attrition-dataset)
2. `python3 scripts/convert_to_parquet.py`
3. `python3 scripts/generate_bad_extract.py` — seeded, reproducible "dirty" extract

### Running `cmd/server` remotely

A second, independent MCP server actually reachable over the network —
same code, same tools, no logic changes — via `TRANSPORT=http`. `Dockerfile`
builds it as a ~28MB static binary with `catalog/` and `data/*.parquet`
baked in:

```bash
docker build -t data-catalog-mcp:local .
docker run -d --rm -p 8092:8091 -e PORT=8091 data-catalog-mcp:local
curl -s -X POST http://localhost:8092 \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"ping","arguments":{}}}'
```

To use it as a normal MCP server — through `cmd/host`, `cmd/client`, or any
other host — point a `client.json` entry at it with `"url"` instead of
`"command"`:

```json
"data-catalog": { "url": "http://localhost:8092" }
```

(swap in a Cloud Run URL once actually deployed there — nothing else about
`client.json` changes). `PORT` is read the same way `TRANSPORT=http` does
locally, since that's the env var Cloud Run itself sets.

## The host + frontend (`cmd/host`, `frontend/`)

`client.json` (`mcpServers`; each entry is either `"command"`, spawned
locally over stdio, or `"url"`, reached remotely over HTTP):

```json
{
  "mcpServers": {
    "data-catalog": {
      "command": "/absolute/path/to/data-catalog-mcp/bin/data-catalog-mcp",
      "env": { "CATALOG_PATH": "...", "DATA_DIR": "..." }
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/absolute/path/to/data-catalog-mcp"]
    },
    "git": {
      "command": "python3",
      "args": ["-m", "mcp_server_git", "-r", "/absolute/path/to/data-catalog-mcp"]
    }
  }
}
```

`filesystem` needs nothing installed (`npx` fetches it on first run);
`git` needs `pip3 install --user mcp-server-git`.

**`cmd/host`** connects to every server in `client.json` at startup, exposes
their combined tools to the chat model, and serves two HTTP endpoints on
`:8090`:

- `GET /api/servers` — the connected servers and the tools each one offers,
  plus the active `LLM_MODEL`/`LLM_API_URL` — for the frontend's sidebar/header.
- `POST /api/chat` — takes `{history, message}`, streams the turn back as
  server-sent events (`round_start`, `delta`, `reasoning_delta`,
  `tool_call_start`, `tool_call_result`, `done`, `error`) instead of one
  blocking response.

Talks to any OpenAI-compatible `/chat/completions` endpoint via `internal/llm`
(just a URL — Ollama's `/v1`, OpenAI, vLLM, llama.cpp, OpenCode Go, whatever),
configured via env vars / `.env`:

| Variable | Description |
|---|---|
| `LLM_API_URL` | Base URL, e.g. `http://localhost:11434/v1` or `https://api.openai.com/v1` |
| `LLM_MODEL` | Model name, e.g. `qwen2.5:7b-instruct` or `gpt-4o-mini` |
| `LLM_API_KEY` | API key (empty for local Ollama) |
| `HOST_ADDR` | `:8090` by default |
| `CLIENT_CONFIG` | `client.json` by default |

```bash
go run ./cmd/host
```

Tool names are qualified `<server>__<tool>` (e.g. `git__git_status`) so tools
from different servers never collide.

**`frontend/`** is a React + Vite chat UI that talks only to `cmd/host`:

```bash
cd frontend
bun install
bun dev
```

Set `VITE_API_URL` if `cmd/host` isn't on the default `http://localhost:8090`.

**`cmd/client`** — one call at a time, for debugging:

```bash
go run ./cmd/client                                          # list every tool, grouped by server
go run ./cmd/client call <server> <tool> '{"json":"args"}'   # call one tool
go run ./cmd/client call data-catalog ping
go run ./cmd/client call git git_status '{"repo_path":"/abs/path"}'
```

Reads `client.json` from the working directory by default (`-config` to override).
